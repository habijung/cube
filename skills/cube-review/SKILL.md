# Code Reviewer

커밋 전 변경사항 또는 지정된 파일에 대해 코드 리뷰를 수행합니다. 기본으로는 채팅에 짧은 결과만 출력하며, `--save` 또는 `--clear`가 지정된 경우에만 상세 결과를 `.cube/review.md`에 저장합니다.

## 사용법

```bash
/cube-review                       # 기본: 전체 변경을 일반 리뷰 모델로 검토
/cube-review src/Foo.m             # 특정 파일 리뷰
/cube-review abc1234               # 특정 커밋 리뷰
/cube-review abc1234..def5678      # 커밋 범위 리뷰
/cube-review --heavy               # 이번 리뷰에 상위 비용 등급의 모델 사용 허용
/cube-review --save                # 상세 결과를 .cube/review.md 맨 위에 추가
/cube-review --clear               # 기존 기록을 이번 상세 결과로 교체
```

---

## 출력 원칙

- **계획·진행 상황을 중간에 출력하지 마십시오.** "Step 1을 수행합니다", "diff를 수집합니다" 등의 사전 선언은 금지입니다.
- **짧은 최종 결과만 출력하십시오.** 리뷰 완료 여부와 판정, 남은 필수 지적과 사용자가 판단할 사항만 알리세요. 필수 지적이 있으면 파일·라인과 해당 지적의 근거를 짧게 포함하세요. 권장 지적은 사용자 판단이 필요한 경우에만 채팅에 포함하세요. 리뷰가 미완료이면 사유를 알리고, 통과나 지적 없음으로 표시하지 마세요.
- **상세 리뷰는 채팅에 다시 작성하지 마십시오.** 저장을 요청한 경우에만 저장 경로 또는 저장 실패를 최종 결과에 포함하세요.

## 실행 절차

### Step 1 — 초기화

다음 정보를 수집하십시오:

1. **플래그 파악:** `--heavy`, `--save`, `--clear` 유무를 기록하십시오. `--clear`는 저장을 포함하며, `--save`와 함께 지정하면 `--clear` 동작을 적용합니다.
2. **인자 타입 감지:** 플래그를 제외한 첫 번째 인자를 분석하여 리뷰 모드를 결정하십시오.

   | 조건 (위에서부터 첫 일치)             | 모드      | diff 명령어                                                            |
   | :------------------------------------ | :-------- | :--------------------------------------------------------------------- |
   | 인자 없음                             | 워킹트리  | `git diff --no-relative HEAD`                                          |
   | 인자가 `./` 또는 `../`로 시작          | 파일 경로 | `git diff --no-relative HEAD -- ":(literal)$path"`                      |
   | 인자가 `..` 포함 (예: abc123..def456) | 커밋 범위 | `git diff --no-relative <검증된 범위>`                                 |
   | 인자가 16진수 7~40자 (예: abc1234)     | 단일 커밋 | `git -c log.showSignature=false show --no-relative --format= <commit>` |
   | 그 외 (예: src/Foo.m)                 | 파일 경로 | `git diff --no-relative HEAD -- ":(literal)$path"`                      |

3. **변경사항 수집:** 위 모드에 맞는 명령어를 호출한 디렉터리에서 실행하십시오. 파일 경로 모드의 사용자 입력은 호출 위치 기준으로, `:(literal)`을 붙여 하나의 Git 인자로 전달하세요. 모든 모드에서 Git 명령의 경로 인자 끝에 저장소 루트 기준 제외 경로 `':(top,exclude,literal).cube/review.md'`를 붙이세요. 경로 구분자인 `--`가 없다면 제외 경로 앞에 추가하세요.
   - diff를 실행하는 Git 명령에만 `GIT_LITERAL_PATHSPECS=0 GIT_GLOB_PATHSPECS=0 GIT_NOGLOB_PATHSPECS=0 GIT_ICASE_PATHSPECS=0`을 지정하세요. 상속된 설정 때문에 제외 규칙이 비활성화되거나 충돌하면 안 됩니다.
   - 커밋 범위는 `...`를 먼저 찾고, 없으면 `..`로 양 끝을 나누세요. 생략된 끝은 `HEAD`로 해석하세요. 단일 커밋의 해시와 범위 양 끝은 각각 `git rev-parse --verify --end-of-options "${ref}^{commit}"`으로 검증하세요. 범위는 검증된 커밋 ID를 입력과 같은 구분자로 다시 연결해 하나의 인자로 전달하세요. 커밋으로 해석되지 않거나 Git 명령이 실패하면 오류를 보고하고 중단하세요. 실패를 변경 없음으로 처리하지 마세요.
4. 제외 적용 후 검토할 파일 변경이 없으면 "리뷰할 변경사항이 없습니다."를 출력하고 종료하십시오. 저장소 루트의 `.cube/review.md`만 지정한 경우도 여기에 해당합니다.
5. **저장 요청이 있을 때만 헤더 레이블 기록** (`.cube/review.md` 상단에 표시할 메타데이터):
   - 워킹트리 / 파일 경로 모드: `git rev-parse --short HEAD` → `HEAD: <hash>`
   - 단일 커밋 모드: `git rev-parse --short <hash>` → `commit: <hash>`
   - 커밋 범위 모드: 검증된 양 끝 커밋을 각각 짧은 해시로 표시하고 입력과 같은 구분자 유지 → 예: `range: <start>..<end>`
6. 현재 디렉토리에서 AI 컨벤션 파일(`AGENTS.md`, `CLAUDE.md`, `GEMINI.md` 등)이 있으면 경로를 기록하십시오. 단, 동일 파일을 가리키는 symlink는 한 번만 전달합니다 (realpath 기반 dedup) — Step 2에서 리뷰 에이전트에게 컨텍스트로 전달합니다.
7. **Large diff 분할 (token efficiency):** diff가 1500줄을 초과하면 다음 절차로 부분 집합 A·B에 분배하십시오.
   1. **공용 헤더 식별 (양쪽 공통 전달):** `*Define.h`, `*Models.h`, `*Constants.h` 등 enum/타입/상수를 정의하는 헤더 파일은 분할 대상에서 제외하고 양쪽 에이전트 모두에게 전달합니다 (cross-file 네이밍·미러링 패턴 감지 보존).
   2. **prefix 그룹핑:** 같은 디렉토리 prefix를 공유하는 파일은 하나의 그룹으로 묶습니다 (예: `RVmacRXViewerDisplay/**`는 한 그룹, Sender/Receiver 짝은 함께).
   3. **Greedy bin-packing:** 그룹 단위로 줄 수 합계가 균등해지도록 A·B 두 부분 집합에 분배합니다.
   4. **분배:**
      - **Agent 1**에게 `(A의 diff + A의 파일 목록 + 공용 헤더)` 전달.
      - **Agent 2**에게 `(B의 diff + B의 파일 목록 + 공용 헤더)` 전달.
      - 기본적으로 같은 부분 집합을 두 기본 리뷰어에게 보내지 마세요. 단, Step 1-8에서 선정한 담당 위험 구간과 그 판단에 필요한 관련 변경은 다른 부분 집합에 있어도 전달하세요. 이 예외를 위해 부분 집합 전체를 복제하지 마세요.
   5. **단일 파일 예외:** 단일 파일이 1500줄을 초과하는 경우에는 분할하지 않고 그대로 전달하되, 에이전트에게 핵심 변경 로직에 집중하도록 지시하십시오.

   > Rationale: 4점 측정에서 분기는 트리거됐으나 분배 누락으로 비용이 $8.55까지 상승(M8 케이스). 부분 집합 명시 분배 + 공용 헤더 broadcast로 토큰 ~40% 감소를 노립니다.

8. **추가 검토 대상 선정:** 첫 리뷰 결과를 받기 전에, 중요한 문제를 놓쳤을 때 영향이 큰 변경이 있는지 확인하고 해당 주제와 경로·변경 구간을 기록하세요. 예를 들어 권한 검증, 동시성·수명주기, 데이터 손실·되돌리기 어려운 마이그레이션은 Agent 1의 추가 검토 대상이 될 수 있습니다. 승인·배포 절차처럼 중요한 동작을 결정하는 프로젝트 지침 변경은 Agent 2의 추가 검토 대상이 될 수 있습니다. 언어나 확장자, diff 줄 수만으로 결정하지 마세요. diff를 분할한 경우에도 해당 주제의 기본 리뷰어에게 이 구간과 필요한 관련 변경을 전달하세요.

### Step 2 — 리뷰 수행

호스트가 제공하는 sub-agent 도구로 Agent 1과 Agent 2를 **각각 별개의 sub-agent 호출로 dispatch하십시오. 단일 sub-agent 호출에 두 체크리스트를 통합하는 것은 금지합니다.** 두 기본 호출은 단일 메시지에서 동시에 실행하고, 가능하면 병렬/background 옵션을 사용하십시오.

| 호스트      | 도구명       | 호출 형식                                            |
| ----------- | ------------ | ---------------------------------------------------- |
| Claude Code | `Task`       | `subagent_type: general-purpose`, `background: true` |
| OpenCode    | `task`       | `subagent_type: <호스트에 등록된 generalist 계열>`   |
| Gemini CLI  | `generalist` | `generalist(request: string)`                        |
| Pi          | `subagent`   | 호스트가 제공하는 호출 형식 사용                      |

호출 전에 [모델 전략](#모델-전략)으로 각 리뷰어의 모델을 확인하세요. 도구가 있으면 확인된 모델로 두 리뷰어를 호출하되, 비용 등급이나 실제 사용 모델을 확인할 수 없다면 확인을 위해 일단 호출하지 마세요. 모델 확인·실행에 문제가 있으면 미완료 사유를 보고하고, 기본 모델이나 부모 모델로 몰래 다시 시도하지 마세요.

> sub-agent 도구가 없는 호스트에서는 현재 메인 에이전트의 모델에 동일한 비용 확인 및 승인 조건을 적용하세요. 비용 등급을 확인할 수 없거나, 현재 모델이 상위 비용 등급인데 그 사용이 승인되지 않았다면 자체 검토도 시작하지 말고 미완료 사유를 보고하세요. 조건을 충족하면 두 체크리스트를 순차적으로 적용할 수 있지만, 이 경우 독립 리뷰가 아니며 독립 리뷰가 필요한 절차를 통과한 것으로 보고하지 마세요.

각 에이전트에게 전달하는 프롬프트의 **맨 첫 줄에 반드시** 다음 문장을 포함하십시오 (anti-bias):

> **이 메시지 외의 어떤 사전 컨텍스트나 의도 추정도 고려하지 마십시오. 아래 전달된 코드와 메타데이터만 보고 객관적으로 판정하십시오.**

이어서 각 에이전트에게 다음 정보를 전달하십시오:

- 해당 에이전트에게 할당된 diff (Step 1-7에서 분할된 경우 부분 집합 A 또는 B + 공용 헤더 diff; 분할되지 않은 경우 diff 전문). 기본 리뷰어에게는 Step 1-8에서 선정한 담당 구간과 그 판단에 필요한 관련 변경도 포함하세요.
- 전달한 diff에 대응하는 변경 파일 및 관련 파일 목록
- 프로젝트 루트 경로
- AI 컨벤션 파일 경로 (있을 경우, symlink dedup 후)
- 검토 대상 버전에 적용되는 명시적 요구사항이나 동작 계약 (확인할 수 있는 경우, 관련 부분과 출처만 전달하고 첫 리뷰 결과나 구현자의 자기평가는 제외)
- 해당 에이전트의 체크리스트 (아래 "Agent 1" 또는 "Agent 2" 섹션 전체)
- 심각도 판정 룰(🔴/🟡)과 False positive 제외 룰 (아래 본문 그대로)
- [리뷰 결과 형식](#리뷰-결과-형식) 전체 (지적 있음·없음·미완료 구분)

각 에이전트는 이슈마다 심각도를 판정하십시오:

- 🔴 **[필수]**: 동작 오류 또는 보안 취약점. 즉시 수정 필요.
- 🟡 **[권장]**: 수정하면 좋으나 블로커는 아님.
조치할 내용이 없는 참고 사항이나 칭찬은 작성하지 마세요. 기존 권장 지적에 해당하는 구체적인 개선은 **[권장]**으로 남기세요.

**False positive로 제외할 항목:**

- 이번 변경과 무관한 기존 문제. 영향을 받는 코드가 변경되지 않았더라도, 이번 변경이 새로 일으킨 회귀는 원인이 된 변경과 영향을 받는 경로를 근거로 보고하세요.
- 컴파일러/린터가 처리할 수 있는 타입 오류, 임포트 누락
- 확인된 요구사항이나 동작 계약에 따른 의도된 동작 차이 자체. 그 변경이 별도로 일으킨 회귀는 제외하지 마세요. 의도를 추정해 회귀를 무시하거나, 요구사항이 불명확하다는 이유만으로 결함으로 단정하지 마세요.
- 이미 주석으로 무시된 이슈

#### 위험이 큰 주제의 독립 2차 검토

- Step 1-8에서 선정한 위험 구간을 Agent 1·2의 **리뷰 영역별**로 묶고, 필요한 영역에만 **새 리뷰어를 한 명씩** 추가하세요(최대 두 명). 첫 리뷰에서 지적이 없어도 실행합니다. 같은 영역의 두 리뷰어에게 **동일한 위험 구간, 관련 변경·공용 헤더, 체크리스트**를 전달하되, 추가 리뷰어에게 첫 결과나 판단을 전달하지 마세요. 추가 리뷰어도 관련 로컬 파일을 실제로 읽어야 합니다.
- 기본·추가 검토와 수정 후 재리뷰에서는 각각 **전달한 diff와 판단에 실제 사용한 로컬 파일·적용 지침이 같은 검토 대상 버전**에 대응하는지 확인하세요. 단계별로 동일한 읽기 전용 스냅샷에서 diff를 생성하고 파일을 읽거나, diff 수집 시점의 대상 버전과 각 리뷰어가 실제로 읽은 내용 버전을 대조하세요. 같은 단계에서 판단 근거가 달라졌거나 diff와 읽은 내용이 같은 버전인지 확인할 수 없으면 미완료로 남기세요.
- 기존 [모델 전략](#모델-전략)을 그대로 적용하세요. 추가 검토가 필요하다는 이유만으로 상위 비용 모델 사용이 승인되는 것은 아닙니다. 필요한 독립 리뷰어를 실행할 수 없다면 해당 검토를 미완료로 남기세요.
- 이 검토는 **수정 전 같은 변경에서 놓친 문제를 찾기 위한 것**입니다. 필수 지적을 수정했다면 해당 구간과 관련 변경을 재검증하고, 수정본에 대한 독립 재리뷰가 끝나기 전에는 리뷰 통과나 커밋 준비 완료로 보고하지 마세요.

#### Agent 1 — 버그 & 아키텍처

다음 사항을 확인하십시오:

- **Null Safety:** null/nil 안전 처리 없이 강제 접근하는 코드
- **File Access:** 파일 존재 확인 없이 바로 접근하는 코드
- **Memory:** 클로저·람다 내부에서 순환 참조가 발생할 수 있는 캡처 패턴
- **Resources:** 리소스(파일 핸들, 연결, 스트림 등) 해제 누락
- **Security:** 보안 취약점 (OWASP Top 10 기준)
- **Architecture:** 프로젝트의 AI 컨벤션 파일에 명시된 아키텍처 레이어 경계 침범
- **Concurrency:** 프로젝트의 표준 비동기/스레딩 패턴 준수 여부
- **Error Handling:** 에러/예외 발생 시 적절한 처리(로깅, 전파, 복구) 없이 무시(silent swallow)하는 코드
- **Requirements:** 확인 가능한 요구사항·동작 계약과 변경된 동작이 일치하는지 확인하세요. 확인할 근거가 없으면 의도를 추정하지 마세요.
- **Tests:** 변경된 동작의 주요 성공·실패·경계 경로를 관련 테스트의 검증 조건이 실제로 확인하는지 살피세요. 테스트 공백은 놓칠 수 있는 구체적인 회귀와 연결해 보고하고, 실행하지 않은 테스트를 통과했다고 하지 마세요.
- **Performance:** 실제로 영향받는 경로에서 반복 I/O, 추가 할당, 복잡도 증가 등 비용이 의미 있게 늘어나는지 확인하세요. 영향받는 경로와 발생 조건을 근거로 삼으세요.
- **Compatibility:** 공개 API·CLI·설정·저장 형식이 바뀌면 기존 호출자와 데이터가 호환되는지 확인하세요. 호환되지 않는 변경이라면 프로젝트가 요구하는 마이그레이션 경로와 안내가 있는지 확인하세요.
- 로컬 파일의 해당 라인을 실제 Read하여 맥락을 확인하십시오.

#### Agent 2 — 네이밍 & 컨벤션 & 문서

다음 사항을 확인하십시오:

- **Naming:** 프로젝트의 AI 컨벤션 파일에 명시된 네이밍 규칙 준수 여부
- **Convention:** 변수·함수·타입 이름이 프로젝트 컨벤션과 일치하는지
- **Structure:** 섹션 구분자가 적절히 사용되고 있는지
- **Compliance:** 프로젝트의 AI 컨벤션 파일이 명시적으로 요구하는 사항을 변경사항이 위반하는지
- **Docs:** 경로·매핑·상수, CLI 옵션, 설정, 기본 동작, 운영 절차가 바뀌면 관련 문서와 사용 예시가 실제 동작이나 적용 지침과 일치하는지 확인하세요.
- 로컬 파일의 해당 라인을 실제 Read하여 맥락을 확인하십시오.

### Step 3 — 결과 출력

두 기본 리뷰와 필요한 독립 2차 검토의 결과를 대조하세요. 같은 문제는 하나로 합치되, 추가 리뷰어만 발견한 유효한 지적도 반영하세요. 필요한 검토가 미완료라면 통과로 표시하지 마세요. 출력 원칙에 따라 채팅에는 짧은 최종 결과만 남기십시오.

- **기본 실행:** `.cube/review.md`를 읽거나 쓰지 말고, 리뷰 저장을 위해 `.cube/`나 `.cube/.gitignore`를 생성하지 마세요.
- **저장 요청 (`--save` 또는 `--clear`):** 변경사항이 있고 리뷰를 완료한 경우에만, 저장용 상세 결과를 아래 형식으로 한 번 작성하세요. 저장 직전에 `.cube/`가 없으면 생성하세요. `.cube/.gitignore`가 없다면 아래 내용으로 생성하고, 이미 있으면 그대로 두세요.

  ```gitignore
  # Cube - Generated file tracking policy
  # Tracked: plans/ (persistent, git-committed)
  # Ignored: temporary outputs
  review.md
  summary.md
  ```

- **저장 방식:** 새 상세 결과와 헤더를 `.cube/` 안의 임시 파일에 작성하세요. `--save`에서는 기존 로그가 있다면 구분 줄을 넣고 기존 바이트를 임시 파일 뒤에 이어 붙이세요. 파일 간 복사는 Bash에서 처리하고, 기존 내용을 읽기 도구나 명령 출력으로 모델에 가져오지 마세요. `--clear`에서는 기존 내용을 읽거나 이어 붙이지 않습니다. 임시 파일이 완성된 뒤에만 `{project_root}/.cube/review.md`를 교체하세요. 기존 파일을 먼저 삭제하지 말고, 저장이 실패하면 기존 기록을 보존하고 임시 파일을 정리하세요.
- **저장 헤더** (모드별 형식):
  - 워킹트리 / 파일 경로: `# YYYY-MM-DD HH:MM | HEAD: <hash>`
  - 단일 커밋: `# YYYY-MM-DD HH:MM | commit: <hash>`
  - 커밋 범위: Step 1의 범위 레이블 사용 (예: `# YYYY-MM-DD HH:MM | range: <start>..<end>`)

## 리뷰 결과 형식

아래 형식은 **개별 리뷰어 응답과 요청 시 저장하는 결과**에 적용합니다. 채팅의 최종 결과는 [출력 원칙](#출력-원칙)을 따릅니다.

- **지적 있음:** 필수 지적부터 한 항목씩 작성하세요. `등급 · 파일:라인 · 문제와 영향 · 권장 조치`를 포함하고, 판정(`✅ 승인` / `⚠️ 조건부 승인` / `❌ 수정 필요`)을 덧붙이세요.
  - 예: 🔴 **[필수]** `path/to/file:42` — 실패가 성공으로 처리되어 호출자가 재시도하지 않습니다. 실패를 호출자에게 전파하세요.
- **지적 없음:** 담당 검토를 완료했고 필수·권장 지적이 모두 없는 경우에만 `지적 없음 — ✅ 승인`으로 답하세요. 개별 리뷰어는 자신의 담당 범위를 넘어 검토를 완료했다고 주장하지 마세요.
- **미완료:** `미완료 — <완료하지 못한 검토와 사유>`로 표시하세요. 이미 확인한 지적이 있다면 같은 형식으로 함께 남기되, 통과나 지적 없음으로 표시하지 마세요. 미완료 결과는 저장하지 않습니다.

변경 전체 요약, Before/After 코드, 복수 대안과 장단점 비교는 기본으로 넣지 마세요. 지적의 타당성이나 영향 판단에 필요한 경우에만 그 근거를 짧게 덧붙이세요.

## 모델 전략

1. **비용 등급 확인:** 현재 호스트에서 실행 가능한 모델과 실제 사용될 모델을 확인하세요. 일반·상위 비용 등급은 사용자가 지정한 기준을 우선하고, 기준이 없다면 현재 결제 방식에 적용되는 가격 또는 사용량 등급처럼 확인 가능한 근거를 사용하세요. 모델 이름, 코드 양, 부모 모델의 등급만으로 비용을 추정하지 마세요. 호스트에 모델이 표시된다는 사실만으로 비용 등급이 확인된 것은 아닙니다.
2. **기본 실행:** 두 리뷰어의 체크리스트와 변경의 난이도를 고려해, 일반 비용 등급에서 검토에 충분한 모델을 각각 선택하세요. 선택한 모델은 호스트가 지원하는 실행별 지정 방식으로 적용하세요. 직접 지정할 수 없다면 호스트가 사용할 모델과 비용 등급을 확인할 수 있을 때만 실행하세요. 기본값이나 부모 모델이 자동으로 적합하다고 간주하지 말고, 일반 등급에서 충분한 모델을 확인할 수 없으면 그 이유를 알리고 확인을 기다리세요.
3. **상위 모델 사용:** 사용자가 `--heavy`를 지정하거나 이번 리뷰의 상위 모델 사용을 명시적으로 승인한 경우에만, 필요한 범위에 상위 비용 등급 모델을 선택하세요. `--heavy`는 상위 모델 사용을 허용하는 옵션이며 두 리뷰어 모두를 상향하라는 뜻은 아닙니다. 승인 범위 밖으로 모델 등급이나 검토 범위를 확대하지 마세요.
4. **검토 중 불확실성이 남을 때:** 두 리뷰어의 결론이 충돌하거나 커밋 여부에 영향을 주는 판단이 남으면, 무엇을 왜 상위 모델로 다시 검토해야 하는지 알리세요. 승인받은 뒤에도 그 부분만 독립적으로 재검토하세요. 승인 전이거나 적합한 모델을 확인하지 못했다면 해당 판단을 미해결로 남기고, 독립 리뷰 통과나 커밋 준비 완료로 보고하지 마세요.
